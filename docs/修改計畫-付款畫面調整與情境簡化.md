## 三、付款流程畫面：處理中與失敗

沿用 `#paymentModal` 既有的 `.pay-view` 骨架（現有 `#paySummaryView` 帶 `active`），新增兩個同層 view。**付款成功不是一個停留畫面**——它只是「轉圈圈處理中」之後的自動結果（關窗＋進入步驟四＋toast），因此不需要獨立的「付款成功」view。

### 3.1 付款處理中 `#payProcessingView`

```
🔄 轉圈圈 spinner（沿用 js/ui/Generation.js #spinner 的動畫樣式）
文案：付款處理中，請稍候…
明細：訂單編號 <span id="payProcessingOrderNo">
```

- 無任何按鈕，使用者無法在此畫面手動操作（可保留關閉鈕但點擊等同取消，見 3.3）。
- 這是一個**純 UI 過渡效果**，用來呈現「等候金流端回應」的等待感，不代表真的有 API 呼叫。

### 3.2 付款未完成 `#payFailedView`（取消與失敗共用同一畫面）

```
⚠️ 警示圖示（沿用 .gen-error-icon 的 SVG 樣式，class 取 pay-error-icon）
標題：付款未完成
說明：本次交易並未完成，系統未向您收取任何費用。您可以重新付款，或返回上一步調整設定。
明細：訂單編號 <span id="payFailedOrderNo">
按鈕：#payRetryBtn「重新付款 ›」(btn-primary)
      #payFailedBackBtn「返回上一步」(btn-secondary)
      聯絡客服連結 mailto:scholarcoach.ai@gmail.com（沿用 #genErrorContactBtn 樣式）
```

- **取消與失敗不做文案分流**，共用上述同一段說明，不需要 `failReason` 參數。
- 「重新付款」→ 切回 `#paySummaryView`，**保留原訂單編號與已填發票資訊**（不呼叫 `resetInvoiceState()`）。
- 「返回上一步」／右上角關閉鈕／點擊遮罩 → 關閉彈窗，畫面停留在步驟三，**不得**進入步驟四。
- 這條路徑**絕不**呼叫 `onSuccess()`、不寫入 `state.usageRecords`、不修改 `state.user.hasUsedFreeTrial`。

### 3.3 View 切換

在 `js/ui/Member.js` 新增一個小工具函式集中管理，避免各處散落 `style.display`：

```js
function showPayView(id) {
  document.querySelectorAll('#paymentModal .pay-view')
    .forEach(v => v.classList.toggle('active', v.id === id));
}
```

並對外匯出一個情境入口（供 Demo 面板呼叫）：

```js
export function showPaymentFailed()      // 填入訂單編號 → showPayView('payFailedView')
```

`payProcessingView` 不需要對外匯出——它只在 `#startPayBtn` 的正常付款流程中於 `Member.js` 內部呼叫 `showPayView('payProcessingView')` 即可（見第五節），Demo 面板不會用到。

`openPaymentModal()` 開窗時一律先 `showPayView('paySummaryView')`，避免上一次殘留在處理中或失敗畫面。

## 四、Demo 面板新增一顆按鈕

付款成功情境不再另設 Demo 按鈕——使用者在正常流程（步驟三「開始生成」→ 確認訂單 → 前往付款）走一次即可看到完整的成功效果（見第五節），無需在 Demo 面板重複呈現。Demo 面板僅新增「付款未完成」一顆按鈕，用來直接展示正常流程走不到的失敗結果畫面。

### 4.1 `index.html`（`#demoPanel` 內，接在「(4) 生成中：網路/伺服器錯誤」之後）

```html
<div class="demo-panel-header" style="margin-top:8px;">付款情境 Demo</div>
<button class="demo-panel-btn" id="demoPayFailed">(3) 付款：取消／失敗</button>
```

### 4.2 `js/ui/DemoPanel.js`

沿用既有慣例：先 `requireLoginForDemo()`，再 `goStep(3)`，接著開啟確認訂單彈窗並直接展示失敗結果畫面（不需要等待感）：

```js
const payFailedBtn = document.getElementById('demoPayFailed');
if (payFailedBtn) {
  payFailedBtn.onclick = () => {
    if (!requireLoginForDemo()) return;
    goStep(3);
    openPaymentModal({ amount: 30, desc: '分析生成研究提案（Demo 情境）', onSuccess: () => {} });
    showPaymentFailed();
  };
}
```

- 此處 `onSuccess: () => {}` 僅為滿足 `openPaymentModal()` 的參數格式，實際上此按鈕的操作路徑必然導向失敗畫面，`onSuccess` 不會被呼叫。
- 需在 `DemoPanel.js` 頂部從 `./Member.js` 匯入 `openPaymentModal`、`showPaymentFailed`。

## 五、正式流程的銜接（`#startPayBtn`）

```
點擊前往付款
  └─ validateInvoice() 失敗 → 停在明細畫面顯示欄位錯誤（現況不變）
  └─ validateInvoice() 通過 → 存 invoiceInfo → showPayView('payProcessingView')（轉圈圈，模擬等候金流端回應）
       └─ 短暫延遲後（本次以 setTimeout 模擬，例如 800ms；不呼叫任何真實或模擬 API）
            → 關閉彈窗 + goStep(4) + 右上角 toast「付款成功！開始為您分析生成研究提案...」+ onSuccess()
              （onSuccess() 內含寫入 state.usageRecords 與呼叫 runGeneration()，此部分行為與現況相同，定義在 js/app.js，不需異動）
```

正式版備註（寫在程式碼註解即可，本次不實作）：`#payProcessingView` 呈現期間，正式串接時會等候金流端的付款結果 callback／查詢 API；收到成功結果才會執行上述關窗與收尾動作，若收到取消或失敗結果則改為顯示 `#payFailedView`（本次僅由 Demo 面板單獨觸發此畫面，正式流程的失敗判斷不在本次範圍）。
